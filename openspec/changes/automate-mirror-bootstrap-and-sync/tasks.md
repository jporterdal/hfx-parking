Section 1 proves the one assumption everything else rests on: that `sync()` populates a truly empty database. Section 2 adds the lock, section 3 makes a layer failure local, and section 4 builds the worker on top of both. Section 5 is the readiness state and how the served application uses it. Section 6 reconciles the documentation and writes the Railway runbook. Section 7 verifies on Railway what cannot be verified anywhere else.

Do section 1 first: if the empty-database run fails, the design's premise (D1, one worker over the existing sync) needs revisiting before anything is built on it.

## 2. The sync lock (D3, advisory lock at the entry points)

- [ ] 2.1 Add the lock to `src/mirror/db.py`: a context manager that takes a session-level `pg_try_advisory_lock` on a fixed key, raises `SyncInProgress` when another session holds it, and releases on exit. Verify with database tests that: with two connections one wins and the other gets `SyncInProgress`; a `commit()` and a `rollback()` on the holder do not release it; and terminating the holder's backend (`pg_terminate_backend`) frees it so the second connection then succeeds
- [ ] 2.2 Add `db.sync_lock_held(conn)`, which reports whether another backend currently holds the lock by reading `pg_locks`, and verify with a database test that it is true while a second connection holds the lock and false after that connection closes
- [ ] 2.3 Take the lock in `sync.py`'s `main()` for every mode that writes (a normal run, `--poll-only`, `--force-pull`, `--reload`) and in `load.py`'s `main()` for every mode that writes (including `--restart`), leaving the read-only modes (`--history`, `--versions`, `--report`) unlocked, and apply the schema inside the lock. Verify with a test that starts each entry point while another connection holds the lock and confirms a non-zero exit, a message saying a run is in progress, and no change to the staging table or `sync_runs`
- [ ] 2.4 Verify no library function takes the lock by accident: run the existing `tests/test_sync.py` and `tests/test_load_rows.py` unchanged and confirm they still pass with many connections in one process

## 4. The worker (D1 and D2, one worker service and its loop)

- [ ] 4.1 Add `src/mirror/worker.py` with the loop from D2 (check configuration, take the lock, apply the schema, sync, release, then sleep for the computed delay), with the clock and the sleep injectable. Verify with tests using a fake clock that: after success the delay is the earliest `next_due_at` minus now, never below five minutes; after a failure it is the one-hour backoff whatever `next_due_at` says; after a busy lock it is the five-minute retry and nothing is recorded as a failure; an exception inside a cycle is caught, logged and becomes a failure backoff; and a missing `PG*` variable at start exits non-zero
- [ ] 4.2 Verify the worker takes the lock and applies the schema before the first sync, with a test that starts it against a database with no schema and checks the order of events and that the mirror ends up populated (stubbed source)
- [ ] 4.3 Verify the retry floor in a test that makes every sync fail and confirms the worker never starts a second attempt sooner than five minutes after the first, however many cycles run
- [ ] 4.4 Run the worker locally against a throwaway schema (`HFX_MIRROR_SCHEMA`) and the real source, send SIGTERM during the `custom_fields` staged copy, start it again, and verify the log says it is resuming the staged copy and the run completes; keep the throwaway schema's size and elapsed time in the notes for 7.2

## 5. Readiness, and what the served application does with it (D5 and D6)

- [ ] 5.1 Add `status.mirror_readiness(conn)` returning `uninitialised`, `awaiting first load`, `loading` or `ready` by the rules in D5, and verify with database tests for each: no schema; schema with nothing loaded and no lock; the same with the lock held by another connection; all three layers with `full_load_completed_at` set; and a completed mirror with the lock held, which stays `ready`. Include the killed-run case: terminate the backend that held the lock and confirm the state reads `awaiting first load`, not `loading`
- [ ] 5.2 Carry the readiness state on `/api/freshness` and skip the overdue state for a mirror that has never completed a load, and verify with tests that the payload names the state, that `next_update.overdue` is false before the first load even when the recorded due time is long past, and that the existing freshness tests still pass
- [ ] 5.3 Answer a missing schema with a 503 and a body naming the `uninitialised` state on every route that reads the database, instead of an unhandled error. Verify with a test that enumerates the routes from the application's URL map (so a route added later is included), points the application at a schema that does not exist, and asserts no route returns a 500 and each data route returns the 503 body
- [ ] 5.4 State the readiness in the export header when the mirror is not ready, beside the sync time it already states, and verify with a test on both export routes for the not-ready and the ready cases
- [ ] 5.5 Build the not-ready view from D9 (the not-ready view, and how it ends) in `web/app/index.html`: while the state is not `ready`, show one message panel in place of the doorway list, the block list, the map and the filters that act on them, keep the freshness banner carrying the same state, and use the D9 wording for each of the three states with no duration and no progress figure. Read a 503 from `/api/freshness` as `uninitialised` using the state in its body. Verify with `tests/test_page_claims.py`-style tests that the page holds the wording for each state, never the overdue wording for a never-loaded mirror, and no stated duration, and by opening the page against a scratch database in each state and confirming in a browser that no empty list, table or map is visible
- [ ] 5.6 Make the not-ready page recover by itself: poll `/api/freshness` every 30 seconds only while the state is not `ready`, reload the page once when it becomes `ready`, and leave the message in place and try again at the next tick when a fetch fails for any other reason. Verify with a browser-level or scripted-DOM test using a fake fetch and a fake clock that: a 30-second tick with the state still `loading` changes nothing and schedules the next; the tick that returns `ready` triggers exactly one reload; a network error or a non-JSON body keeps the message and does not reload; a page opened on an already-ready mirror makes no polling request; and by loading the page against a scratch database, starting the worker, and confirming the page fills in within a minute of the first load finishing with no manual reload
- [ ] 5.7 Verify the web application never applies the schema: a test that boots the application against a database whose schema is absent and confirms the schema is still absent after a request to each route
