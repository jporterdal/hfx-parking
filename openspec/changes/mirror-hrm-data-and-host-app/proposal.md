## Why

The pipeline re-queries HRM's ArcGIS service on every run and writes its output as one self-contained HTML file. Both choices were correct for a three-hour build and neither survives the next step. Measured live on 2026-09-15:

- **The current fetch shape is the slow one.** One violation type takes 3 minutes 31 seconds, almost all of it spent on `WHERE REQUEST_ID IN (...)` chunk queries at roughly six seconds each. Straight offset paging against the same layers runs at **0.52 seconds per 1,000 rows**.
- **Copying everything is cheaper than fetching one type.** The custom-fields layer is 1,156,710 rows across 88 field names, of which the seven parking attributes are 776,298. The requests layer is 478,458 rows. Loaded in full, both together plus the census polygons came to **1,640 pages, 25 minutes 10 seconds and 375.5 MB on disk**, against the 3 minutes 31 seconds the current pipeline spends to answer a question about one violation type out of thirty.
- **Incremental sync is nearly free.** A watermark on `ObjectId` captures every insert, because new rows arrive with new ids. (An earlier draft justified this by claiming `ObjectId` is monotonic with recency; measurement disproved that — see `design.md` M2 — without disturbing the watermark, which depends on insertion order rather than date order.) The only rows that mutate after insertion are the **3,351 requests still open**, whose `DATE_CLOSED` is filled in later — refetching that entire set costs four pages. An incremental sync is a few thousand rows and takes seconds.
- **The nightly schedule is not matched to anything measured.** Running all thirty canonical violation types the current way would cost roughly 35 to 45 minutes and about 370 requests against a public municipal endpoint every night. The sibling change justifies the nightly cadence by describing the source as "weekly-refreshed," a claim that appears once, unsourced, and is supported nowhere in `docs/`. HRM publishes no refresh-interval documentation this change was able to find. What HRM does publish, on each layer's metadata, is `editingInfo.lastEditDate` — the service requests layer read 2026-09-13 10:34 UTC and its custom-fields layer 10:38 UTC on 2026-09-15, four minutes apart, so the two are loaded together. That single cheap field is a better basis for a sync cadence than an assumed interval.

The hosting requirement lands on the same decisions. The board must be reachable at a URL by HRM coordinators and parking enforcement officers during a demo, with triage decisions shared between them. Today shared triage has exactly one implementation — `window.claude.use("db")` in `web/template.html` — which resolves to `null` on any host that is not a Claude Artifact, silently degrading every viewer to a private `localStorage` copy. `README.md` promises the opposite: "The hosted copy shares those decisions with everyone who opens it, so a team triages one list instead of three."

A third motivation is already visible in the repository. `README.md` and the documents under `docs/` state 9,791 calls, 363 doorways and 71 blocks. A run today produces 9,834, 351 and 70. The figures are hand-written into prose and have drifted from generated output within days — exactly the failure the sibling change records as D17, arriving ahead of schedule. A public URL makes that drift a credibility problem rather than a tidiness problem.

## What Changes

- **Mirror the three HRM layers the product reads into a local relational store.** A full initial load of the requests layer, the custom-fields layer, and the census dissemination areas, by offset paging rather than by identifier chunks. `311_Call_Details` is deliberately excluded (see Impact).
- **Sync incrementally, paced by the source's own update clock.** Poll each layer's `editingInfo.lastEditDate` — one small request, no paging — and sync when it advances. Advance an `ObjectId` watermark per layer to capture inserts, and refetch in full the set of requests still open so that later closures and outcome edits land. Record the outcome of every sync attempt, successful or not, and record the observed interval between source updates so the cadence is measured rather than assumed.
- **Derive the analysis from the mirror rather than from the network.** Doorway grouping, block rollup, ranking and effectiveness evidence read local tables. Their behaviour is unchanged; only their source is. This makes running every canonical violation type a grouping operation over data already held rather than thirty more passes over the network.
- **Serve the board as a hosted web application.** Replace the single generated file with an application served over HTTP, reading derived data through an API, with a route per canonical violation type.
- **Persist triage decisions in the store, shared across viewers.** Replace the Claude-capability binding with shared server-side storage, so decisions reach colleagues on any host.
- **Identify a viewer by role, not by account.** A viewer selects Coordinator or Parking Enforcement Officer on entry; that role is attributed to their triage decisions. This is a demo affordance, not authentication, and the application says so.
- **Filter interactively.** The parameters that are command-line arguments today — district, minimum recent calls per doorway, minimum still-calling doorways per block, and the recurrence window — become controls in the portal, so a coordinator can narrow a list to their own district or widen a threshold without a rebuild.
- **Show four clocks on the page, and say whose limit each one is.** Every view states when HRM last updated the source, the most recent call the data holds, when the mirror last synced successfully, and when the next sync is due. Where the data is behind, the portal distinguishes a lag at HRM's end from a failure at ours, and flips to an overdue state when a scheduled sync has not happened.

Retired, with the reasoning that justified them:

- **One self-contained file** (sibling `design.md` D11). Justified as "a work list that needs infrastructure to open is a work list nobody opens." A hosted URL removes the infrastructure from the viewer's side entirely.
- **Embedded map geometry** (D12). 490 KB of the 611 KB board is `web/map-network.json`, embedded because a single file cannot depend on an external service. A served application can fetch it once and cache it.
- **Shared state through a Claude capability** (D13). The disclosure requirement it introduced survives and is strengthened; the storage mechanism does not.
- **Stateless runs against the live source** (D14). Argued as "at this scope the snapshot buys nothing," which held for one violation type and does not hold for thirty.

Non-goals: mirroring or analysing `311_Call_Details`, real authentication or per-person accounts, deployment and infrastructure mechanics (handled outside this change), coordinate-keyed addressing (unblocked here, deliberately not taken — see `design.md` M9), effect measurement of an installed remedy, and per-address remedy recommendation.

## Capabilities

### New Capabilities

- `hrm-data-mirror`: Hold a local copy of the HRM layers the product reads, load it fully on first run, advance it incrementally on a schedule by monotonic identifier while refetching the mutable open-request set, and record the provenance and success of every sync so that staleness is observable rather than inferred.
- `hosted-triage-app`: Serve the doorway list, the block list and the map over HTTP with a route per canonical violation type, identify a viewer by selected role rather than by account, persist triage decisions to shared storage so every viewer sees the same list, and display mirror freshness on every view.

### Modified Capabilities

- `parking-data-ingest`: Selection, joining, address reduction, doorway location and census placement read the mirror instead of querying ArcGIS per run. Paging and retry are removed rather than modified — the network fetch moves out of this capability and into `hrm-data-mirror`.

### Retired Capabilities

- `triage-board`: Retired in full, replaced by `hosted-triage-app`. Five of its nine requirements rest on the board being one generated file — self-contained, built alongside the briefs, carrying a build time, sharing decisions only where the host happens to offer storage — and those premises do not survive a served application. The remaining four are required unchanged and are restated in `hosted-triage-app`. No behaviour is dropped; each removed requirement names where it now lives.

`doorway-watchlist`, `block-rollup`, `enforcement-effectiveness` and `text-briefs` are unchanged in behaviour by this change and are not restated here.

**A note on the baseline.** `openspec/specs/` holds no capabilities. The six this change builds on are defined in `add-parking-hotspot-map`, whose sections 1 to 7 are built and whose sections 8 to 14 are not. The deltas above are written against that change's specs as the baseline.

That change is superseded by this one rather than continued. Its outstanding work divides in three, and the division matters because only one third can honestly be called done:

- **Delivered by this change's architecture.** The census-fetch retry asymmetry (D14a) disappears when the census layer is read locally. Batching every canonical type stops needing a per-type network pass. Nightly runtime against ArcGIS rate limits stops being a question worth measuring.
- **Carried into this change's tasks, because it is still needed and this change now depends on it.** The daylight-saving correction, run provenance, the explicit recency anchor, the reproducible tow-comparison and closure-time figures, the pure-function test suite, freezing the canonical violation-type list, and computing each type's own effectiveness conclusion. Each is marked in `tasks.md` against its original number. Two of these are hard prerequisites here: the documentation reconciliation cannot quote generated figures that nothing generates, and the per-type routes cannot exist without a frozen type list.
- **Preserved as reasoning rather than as work.** D18 and D19 govern what a violation type may claim, and R1 through R8 record what was tested and rejected. Archiving the change does not retire those conclusions; `design.md` M8 carries the analysis decisions forward intact and this change's 9.8 enforces D19.

Nothing outstanding is marked complete on the basis of being superseded unless it is genuinely delivered by the first category above.

## Impact

- **Existing code.** `src/hotspots.py` splits: its fetch layer is replaced by the mirror, its analysis functions survive largely intact against local data, and its output writers change from file generation to API responses. `web/template.html` becomes the application's markup rather than a substitution target. `web/map-network.json` becomes a served asset. `out/` stops being the product and becomes, at most, an export.
- **New runtime dependencies.** A relational store and an HTTP server where there were none. `README.md` currently states "No keys and no install"; that ceases to be true of the server and remains true of the viewer, who now needs only a browser and a URL.
- **New failure mode, and it is the serious one.** Today a run either completes against live data or fails loudly, and the output cannot be stale without the job having visibly failed. A mirror separates the two: a sync that stops silently leaves an application that looks entirely healthy while serving month-old data. This is the sibling change's D16 concern promoted into production, which is why sync provenance and a staleness warning are requirements of this change rather than follow-up work.
- **Mirror scope and size.** Three layers are mirrored: service requests (478,458 rows), custom fields (1,156,710 rows), and census dissemination areas (610 polygons). Estimated at roughly 300–400 MB on disk with indexes; the implementing work is required to report the observed figure.
- **`311_Call_Details` is excluded, and it is the expensive exclusion to get right.** The layer holds **4,968,536 rows, about 1.2 GB of raw JSON, roughly 28 minutes to pull serially** — larger than everything else mirrored, combined, by a factor of three. The sibling change already dropped it from analysis (R4): it carries `CALL_ID`, `QUEUE_NAME`, `OUTCOME`, `WRAPUP_NAME`, `ARRIVAL_DATETIME` and talk times, with no address, no coordinates and no request identifier, so no per-record join to a service request exists; `OUTCOME` is 99.5 per cent `Handled`, an agent disposition rather than a municipal one; and HRM documents its timestamp as shifted 3–4 hours from true UTC in the opposite direction to the requests layer. Mirroring it would pay that cost for data the product cannot join to anything it publishes.

  This was verified rather than assumed. No 311 call-detail value is read, referenced or implied anywhere in the shipped product: `src/hotspots.py` and `web/template.html` contain no reference to it, and every other occurrence of the string in the repository is one of three benign things — the value `311 Online` of the `INITIATED_BY` field on the **service requests** layer, which is a channel label and not this dataset; a digit sequence inside a census block identifier, a coordinate or a day count; or the two places that record the dataset's rejection, `docs/parking-hotspots/data-sources.md` ("311 Call Details | n/a | Call reason only, no service request join key") and the sibling change's R4.
- **Query volume against HRM falls sharply.** From roughly 370 requests nightly under a thirty-type batch to one cheap metadata poll per cycle and a sync of a few thousand rows only when the source has actually published, after a one-time full load of 1,640 pages.
- **Scope widens cheaply but is not thereby validated.** The mirror holds every violation type, so producing each type's lists costs a grouping operation. It does not establish that the driveway finding transfers to any other type; the sibling change's D19 requirement — that each canonical type's effectiveness evidence is computed and read on its own — still governs what the application is allowed to claim for a type.
- **Coordinate keying becomes cheap.** The sibling change records string address reduction as an interim and coordinate binning as the better answer at wider scope (R2). With data in a spatial store, both the doorway location and the census placement become spatial operations rather than a hand-rolled ray cast. This change does not make that switch; it removes the reason it was impractical.
- **Interpretation limits are unaffected and still carried.** The initiation timestamp remains a staff intake clock, the tow flag remains the only published enforcement outcome, and vehicle identity remains a floor. Moving the data closer does not make any of them stronger.
